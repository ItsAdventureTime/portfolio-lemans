# Writing Style

Write all active app copy, documentation, guides, and commit messages in US
English. Use a professional, conversational tone that respects the reader's
time.

## Voice

- Lead with the outcome, action, or decision.
- Use short, direct sentences and active voice.
- Address the reader as "you" when instructions help them take action.
- Be warm and specific without being casual, salesy, or overly familiar.
- State limits and errors plainly. Explain what happened and what the reader
  can do next.

## Clarity

- Prefer common words: use "use," not "utilize"; "help," not "assist";
  and "before," not "prior to."
- Define an acronym on first use when a non-specialist reader may not know it.
- Use sentence-style headings, meaningful link text, and parallel list items.
- Keep technical identifiers, commands, API names, status values, and legal
  text exactly as required.

## What to avoid

- Hype, vague claims, filler, and repeated summaries.
- Artificially formal language, generic assurances, and unexplained jargon.
- Choppy fragments outside interfaces, commands, tables, and checklists.
- Emoji, slang, and language that blames the reader.

## Document shape

Give each guide one primary purpose. Use the following labels and boundaries:

- **Tutorial**: teach a first successful outcome from start to finish.
- **How-to guide**: solve one known task with concise, executable steps.
- **Reference**: record precise facts, commands, schemas, or constraints without
  turning the page into a walkthrough.
- **Explanation**: describe concepts, architecture, tradeoffs, or rationale.

Link between these types instead of combining all four into one long page. Put
prerequisites and the expected result near the start of tutorials and how-to
guides. Keep reference pages factual and keep roadmap claims separate from
implementation-backed current state.

## Accessible documentation

- Use headings in order and make each heading describe the content that follows.
- Use descriptive link text; do not make a bare URL or “click here” the only
  description of a destination.
- Describe meaningful images and diagrams in nearby text. Mark decorative images
  as decorative rather than assigning them misleading labels.
- Never use color, position, or visual styling as the only way to communicate a
  status or required action. Repeat the meaning in text.
- Give command blocks a clear purpose, required environment, and expected
  result. Keep dangerous or remote commands explicitly labeled and authorized.
- Prefer short paragraphs, lists, and tables that remain readable when zoomed or
  read aloud.

## Editing check

Before you publish text, confirm that it is accurate, readable aloud, uses US
spelling, names the next action when needed, and does not repeat information
already visible nearby.

This standard follows current plain-language, documentation-architecture, and
accessibility guidance:
[Microsoft writing style](https://learn.microsoft.com/en-us/windows/apps/design/style/writing-style),
[Google developer documentation tone](https://developers.google.com/style/tone),
[Digital.gov plain language](https://digital.gov/guides/plain-language/writing),
[Diátaxis](https://diataxis.fr/), and
[WCAG 2.2](https://www.w3.org/TR/WCAG22/).
